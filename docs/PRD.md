## 1. 背景与问题

### 1.1 背景

美食爱好者想找到所在城市的"苍蝇馆子"——藏在小巷子里、环境一般但味道惊艳的小店。这类信息分散在大众点评评论、小红书笔记、本地论坛/贴吧帖子、知乎回答、公众号文章中，**没有结构化聚合**。

### 1.2 用户痛点

1. **信息分散**：要在多个平台反复搜索、人工比对，耗时长。
2. **噪音大**：搜索结果被网红店、探店广告、商家软文占据，真正的老店被淹没。
3. **信息不完整**：帖子里常只有"XX 路菜市场旁边那家面"，缺少准确地址和店名。
4. **信息过时**：多年前推荐的店可能已关门或搬迁。

### 1.3 机会

利用搜索 API + 大模型（LLM）信息抽取 + 地图 POI 校验，自动完成"采集 → 清洗 → 识别 → 去重 → 排序"，输出一份**带证据、可解释**的城市苍蝇馆子榜单。

---

## 2. 产品目标

### 2.1 产品目标

用户输入一个城市名，在可接受的时间内得到一份可信的苍蝇馆子榜单，每家店包含地址、推荐菜、口碑关键词和上榜理由，并可追溯原始出处。

### 2.2 成功指标（MVP）

| 指标 | 定义 | 目标值 |
|---|---|---|
| 榜单准确率 Precision@10 | Top10 中经人工标注确认为"真苍蝇馆子"的比例 | ≥ 70% |
| 网红店混入率 | Top10 中被标注为网红/连锁店的比例 | ≤ 10% |
| 地址可定位率 | 上榜店铺成功匹配到地图 POI 的比例 | ≥ 85% |
| 店名抽取准确率 | 抽取出的店名经人工核对正确的比例 | ≥ 85% |
| 首次生成耗时 | 未命中缓存时，从提交到出榜 | ≤ 5 分钟 |
| 缓存命中耗时 | 命中缓存时的响应时间 | ≤ 2 秒 |
| 单城市生成成本 | LLM + 搜索 API 费用 | ≤ ¥5 |

### 2.3 非目标（MVP 不做）

- 不做全国所有城市覆盖，首批只做 1–2 个城市（如成都、长沙）。
- 不做用户账号、收藏、评论、UGC。
- 不做实时数据（分钟级），以"天/周"为更新粒度。
- 不大规模爬取大众点评、小红书等有强反爬和明确用户协议限制的平台。
- 不做商家入驻、广告、排序干预。

## 3. 目标用户与场景

### 3.1 用户画像

| 用户 | 描述 | 核心诉求 |
|---|---|---|
| 本地吃货 | 在城市生活多年，想发掘没去过的老店 | 要"本地人才知道"的店，不要网红店 |
| 旅行者 | 短期到访，想吃地道的 | 快速得到靠谱短名单 + 地址 + 必点菜 |
| 美食内容创作者 | 找选题 | 想看口碑来源和提及热度 |

### 3.2 用户故事

- **US-1**：作为用户，我输入"成都"，能看到一份苍蝇馆子榜单。
- **US-2**：作为用户，我能看到每家店的地址，并能在地图上定位。
- **US-3**：作为用户，我能看到每家店的推荐菜和口碑关键词（如"分量足""老板实在"）。
- **US-4**：作为用户，我能看到这家店"为什么上榜"，并点开原始帖子核实。
- **US-5**：作为用户，我能按区域、人均价格、菜系筛选榜单。
- **US-6**：作为用户，我能知道数据更新时间，以及某家店是否疑似已关店。

## 4. 核心概念定义

### 4.1 "苍蝇馆子"判定标准

为保证可计算、可评估，本产品将"苍蝇馆子"定义为同时满足以下多数特征的餐饮店：

| 维度 | 正向特征 | 说明 |
|---|---|---|
| 价格 | 人均 ≤ 城市阈值（如 60 元） | 阈值按城市可配置 |
| 环境 | 评价中常出现"环境一般/简陋/小/破" | 与"味道好"共现是强信号 |
| 口味 | 评价中味道相关情感明显为正 | |
| 历史 | 出现"老店/开了十几年/从小吃到大"，或跨多年被持续提及 | |
| 口碑来源 | 被多个独立作者、多个平台提及 | 而非单一账号或单一平台 |
| 位置 | 巷子、菜市场旁、居民区、老小区 | 弱信号 |

### 4.2 "网红店"负向特征

| 特征 | 说明 |
|---|---|
| 营销用语 | 打卡、出片、探店、合作、私信、团购链接 |
| 文案同质化 | 多篇内容高度相似（疑似通稿/水军） |
| 热度突增 | 提及集中在短期内爆发，无长期积累 |
| 连锁属性 | 同名门店在城市内有多家 |
| 价格偏高 | 人均显著高于阈值 |

### 4.3 其他术语

- **提及（Mention）**：一篇文档中对某家店的一次有效描述，包含证据原句。
- **证据（Evidence）**：从原文中截取的、支撑抽取结果的原句，必须能在原文中逐字找到。
- **POI**：地图兴趣点（高德/百度），用于校验店铺真实存在并获取地址坐标。

## 5. 功能需求

### 5.1 功能总览

| 编号 | 模块 | 功能 | 优先级 |
|---|---|---|---|
| F1 | 查询 | 输入城市名，发起榜单生成 | P0 |
| F2 | 查询 | 生成进度展示（采集中/分析中/完成） | P0 |
| F3 | 采集 | 多数据源插件化采集 | P0 |
| F4 | 清洗 | 正文提取、去重、去广告 | P0 |
| F5 | 抽取 | LLM 结构化抽取店名/地址线索/菜品/口碑 | P0 |
| F6 | 校验 | 证据校验，防止幻觉 | P0 |
| F7 | 合并 | 同店实体合并 + POI 匹配 | P0 |
| F8 | 排序 | 苍蝇馆子打分与去网红排序 | P0 |
| F9 | 展示 | 榜单列表 + 店铺详情 + 原文出处 | P0 |
| F10 | 时效 | 时间衰减、关店检测、缓存与增量更新 | P1 |
| F11 | 展示 | 地图视图 | P1 |
| F12 | 展示 | 按区域/人均/菜系筛选 | P1 |
| F13 | 运营 | 管理后台：数据源成功率、成本统计 | P2 |
| F14 | 采集 | 用户手动粘贴链接导入 | P2 |

### 5.2 详细说明

#### F1 / F2：城市查询与进度

- 输入框支持城市名，做标准化（"成都市" → "成都"），不支持的城市给出提示。
- 命中有效缓存：直接返回榜单。
- 未命中缓存：创建异步任务，返回任务 ID；前端轮询或 SSE 展示阶段进度与已处理文档数。
- 同一城市已有进行中的任务时，复用该任务，不重复创建。

#### F3：多数据源采集

- **数据源接口统一**：每个数据源实现 `discover(city, keywords) -> urls` 与 `fetch(url) -> RawDoc`。
- **发现层**：以搜索引擎 API 为主（如 Bing / SerpAPI / Tavily），通过关键词组合 + `site:` 限定覆盖贴吧、知乎、豆瓣、本地论坛、公众号文章等。
- **关键词扩展**：城市名 × {苍蝇馆子, 老店, 本地人才知道, 巷子里, 开了十几年, 好吃不贵, 菜市场 美食}。
- **抓取层**：HTTP 请求优先，失败降级为 Playwright 渲染；正文提取使用通用工具（如 trafilatura）。
- **健壮性**：每个数据源独立限速、超时、重试；单源失败不阻塞整体；记录各源成功率。
- **合规**：仅采集公开页面，遵守 robots；只存储必要摘要与链接，不全量转载原文。

`RawDoc` 字段：`source, url, title, text, publish_time, author, fetched_at`

#### F4：清洗

- 去除导航、评论区噪音、广告段落。
- 基于 URL 和 SimHash 去重（完全重复 + 近似重复）。
- 规则预过滤：段落中既无店名特征（如"XX 面馆""X 记""老 XX"）也无菜品词的，跳过后续 LLM 处理，以节省成本。

#### F5：LLM 结构化抽取

- 输入：清洗后的文档段落 + 城市名。
- 输出：店铺数组（一篇文档可包含多家店），JSON Schema 强约束：

```json
[{
  "name": "王记肥肠粉",
  "address_hint": "XX路菜市场旁边",
  "district": "武侯区",
  "dishes": ["肥肠粉", "锅盔"],
  "aspects": {"味道": "正", "环境": "负", "价格": "正", "服务": null},
  "keywords": ["分量足", "开了二十年"],
  "price_hint": "人均20左右",
  "is_ad_like": false,
  "closed_hint": false,
  "evidence": "XX路菜市场旁边那家王记肥肠粉，开了二十年了……"
}]
```

- 提示词约束：无信息填 `null`，禁止推测或编造；情感按方面分别判断。

#### F6：证据校验

- `evidence` 必须在原文中可匹配（规范化空白和标点后做子串匹配）；不匹配则丢弃该条。
- `name` 必须出现在 `evidence` 或原文中。
- 校验失败率作为抽取质量监控指标。

#### F7：同店实体合并

1. **店名规范化**：去除"店/馆/总店/分店"等后缀，统一全半角、繁简。
2. **POI 匹配**：以"城市 + 规范化店名 + 地址线索"调用地图 POI 搜索，取最优匹配的 `poi_id` 作为主键；同 `poi_id` 合并。
3. **兜底合并**：未匹配 POI 的，按店名相似度 + 区域聚类合并，并标记为低置信度。
4. **POI 补全**：从 POI 获取标准店名、地址、坐标、人均价格、营业状态。
5. **连锁识别**：同一品牌在城市内 POI 数量 ≥ 3 时标记为连锁。

#### F8：打分与排序

- 对每家店计算特征，按加权和得分：

`score = Σ wᵢ × featureᵢ`

| 特征 | 方向 | 计算方式 |
|---|---|---|
| 独立作者数 | + | 去重作者后的提及数（取对数） |
| 平台多样性 | + | 被提及的不同来源平台数 |
| 时间跨度（持久度） | + | 最早到最近提及的年数 |
| 近期热度 | + | Σ exp(-Δt/τ)，τ 默认 365 天 |
| "味道正 + 环境负"共现率 | + | 提及中同时满足的比例 |
| 老店词 | + | 是否出现老店相关描述 |
| 人均价格 | − | 超过阈值越多扣分越多 |
| 营销词比例 | − | 提及中 `is_ad_like` 或含营销词的比例 |
| 文案相似度 | − | 该店提及之间的近似重复比例 |
| 热度突增度 | − | 提及时间分布的集中程度 |
| 连锁标记 | − | 是否连锁 |

- 权重初始为人工设定，基于标注集调参；后续可用逻辑回归学习。
- **防刷**：同一作者多次提及同一家店只计一次。
- **LLM 复核**：对 Top30 送入 LLM，结合证据判断"是否符合苍蝇馆子定义"，输出结论与一句话理由；判定为否的降权。
- 最终输出 Top N（默认 20）。

#### F9：榜单展示

- **列表卡片**：排名、店名、区域、人均、推荐菜（≤3）、口碑关键词（≤5）、一句话上榜理由、最近提及时间。
- **详情页**：完整地址 + 地图定位、全部推荐菜、关键词词频、各维度情感、证据原句列表（附原文链接与来源平台）、得分构成。
- **标记**：低置信度、疑似关店。
- 页面显示"数据更新于 YYYY-MM-DD"。

#### F10：时效性

- **缓存**：每个城市的榜单缓存 TTL 默认 7 天。
- **增量更新**：过期后只搜索最近时间范围内的内容，按 URL 去重，仅处理新文档；LLM 抽取结果按 URL 哈希缓存。
- **关店检测**：POI 营业状态异常或查不到；近期提及中出现"关门/倒闭/搬了"（`closed_hint`）→ 降权并标记。

#### F11 / F12：地图与筛选

- 地图视图展示榜单店铺分布，点击跳转详情。
- 支持按行政区、人均区间、菜系筛选。

## 6. 流程设计

### 6.1 用户流程

```
输入城市 → [命中缓存?] —是→ 展示榜单
                 └—否→ 创建任务 → 展示进度 → 完成 → 展示榜单 → 查看详情/原文
```

### 6.2 数据处理流程

```
关键词扩展 → 搜索发现 URL → 抓取正文 → 清洗去重 → 规则预过滤
   → LLM 结构化抽取 → 证据校验 → 店名规范化 + POI 匹配 → 同店合并
   → 特征计算 → 打分排序 → LLM 复核 Top30 → 生成榜单 → 缓存
```

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 首次生成 ≤ 5 分钟；缓存命中 ≤ 2 秒 |
| 成本 | 单城市生成 ≤ ¥5；LLM 结果缓存复用 |
| 可靠性 | 单数据源失败不影响整体；任务失败可重试 |
| 可扩展性 | 新增数据源只需新增一个插件类 |
| 可解释性 | 每家上榜店必须有证据原句与来源链接 |
| 合规 | 仅采集公开数据，遵守 robots 与限速；不存储个人隐私信息；尊重原作者版权，仅展示摘要并链接原文 |
| 可观测性 | 记录各阶段耗时、各数据源成功率、LLM 调用量与费用、证据校验失败率 |

## 8. 评估方案

1. **构建标注集**：选定 1 个城市，人工标注 50–100 家候选店，标签为"真苍蝇馆子 / 网红店 / 连锁 / 非餐饮 / 已关店"。
2. **抽取评估**：随机抽 50 篇文档人工标注店名，计算抽取准确率与召回率。
3. **合并评估**：抽样检查同店合并结果，计算合并正确率。
4. **排序对比实验**：

| 方案 | 说明 |
|---|---|
| Baseline | 仅按提及次数排序 |
| + 规则打分 | 加入正负向特征 |
| + LLM 复核 | 再加 Top30 复核 |

对比各方案的 Precision@10、网红店混入率，作为迭代依据。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台反爬 / 用户协议限制 | 数据量不足 | 以搜索 API 发现 + 低门槛公开站点为主；不硬爬强反爬平台；支持手动导入链接 |
| LLM 幻觉 | 编造店名或地址 | 证据逐字校验；无信息填 null；POI 二次校验 |
| 同店合并错误 | 一家店被拆成多家或多家被合并 | POI ID 为主键；低置信度标记；抽样评估 |
| 网红店识别不准 | 榜单可信度下降 | 多维负向特征 + LLM 复核 + 标注集调参 |
| 数据过时 | 推荐已关门的店 | 时间衰减、关店检测、增量更新 |
| 成本超预算 | 不可持续 | 规则预过滤、结果缓存、批量调用、选择低价模型 |
| 搜索 API 配额限制 | 采集中断 | 多搜索供应商备选；结果缓存 |
