# 流水线速度优化

首次探一座城市时，用户会在前端看到进度，但生成仍发生在后台。产品目标原先是 **首次 ≤ 5 分钟、已有榜 ≤ 2 秒**。串行跑武汉深筛时已经到十几分钟；成都全流程实测约 **5–6 分钟**。经过下面几轮，首次生成的现实目标是 **1–2 分钟**。已出过榜的城市仍读 SQLite，两秒内返回。

四个大阶段必须按顺序跑（后一步吃前一步的库），优化都发生在**阶段内部**：

```
搜索抽取 → 高德匹配 → 初筛短名单 → 深筛出榜
```

对应代码：`src/alleyfinder/pipeline/run.py`。

---

## 1. 起点：全串行

最初整条链都是 `for` 一条等完再下一条，没有线程池。

| 阶段 | 当时怎么跑 | 大约耗时 |
|---|---|---|
| 发现 | 5 条博查查询串行，再逐篇调 DeepSeek 抽店 | 抽取约 3 分钟 |
| 匹配 | 店名一个一个打高德，中间 `sleep(0.2)` | 约 1 分钟 |
| 初筛 | 本地规则 | 可忽略 |
| 深筛 | 每家店：搜索 → 逐条抓正文（还 `sleep`）→ 调模型，做完才轮下一家 | 武汉 27 家约 10+ 分钟 |

深筛单店大约 20–50 秒，几乎全耗在 `chat()`。抓网页只是附加项，但超时 15 秒的死链会把一家店拖很久。

这一阶段的结论：用户不能盯着页面干等；时间要靠 **跨店并行 LLM** 降下来，不是靠换异步框架。

---

## 2. 少抓注定失败的站

抓正文用 `requests` + `trafilatura`。实测一批 URL：搜狐 / 网易 / 携程 / 本地宝 基本能抽出正文；360 地图、大众点评、马蜂窝、头条、查查吧 几乎全是 JS 空壳或登录墙。

`clients.py` 的 `SKIP_HOSTS` 扩到这些站：命中直接返回空字符串，退回博查摘要，不再空等 15 秒。短于 80 字的抽取也当失败。这是在给后面的并行减负，本身不改变串行结构。

---

## 3. 深筛：店与店并行，但整段绑死

`deep_rank` 抽出 `review_one_shop`，用 `ThreadPoolExecutor`。主线程收结果、写库、报进度。

第一次落地：`MAX_SHOP_WORKERS = 3`。三家店同时跑完整段「搜 + 抓 + 模型」。墙钟大约降到原来的三分之一，但：

- 一家店卡在 DeepSeek 的 30 秒里，那个工人不能去搜下一家
- 博查大部分时间空转
- DeepSeek 也永远只有 3 路，2500 RPM 的额度没用上

```
店1  [搜][抓][========模型========]
店2  [搜][抓][========模型========]
店3  [搜][抓][========模型========]
店4                          [搜][抓][========模型========]
```

---

## 4. 限流只套在博查上

账号档位约 **5 QPS**（充 ¥10）。3 不是官方限额，是当时写死的工人数。

改法：工人开到短名单长度（上限 20），**只有 `search_web` 用信号量卡 5**。搜完立刻释放，当前店去抓正文、调模型，别的店可以接着搜。

```
BOCHA_LIMIT = 5
MAX_SHOP_WORKERS = 20
```

第一版把「搜 + 抓」绑在同一个信号量里：实现简单，但抓正文的十几秒仍占着博查名额。随后把闸缩到 `search_web` 这一句——本地 `fetch_text` 打的是目标站点，不消耗博查配额。

```
店A: [搜 2s] [抓 …]              [DeepSeek …]
店B:      [搜 2s] [抓 …]         [DeepSeek]
店C:           [搜 2s] [抓 …]
         └── 同时最多 5 家在搜；正在抓的店立刻把槽让出来
```

单店顺序仍是：先搜到 URL，再抓这些 URL，再调一次模型。一家店只抽一次口碑，不按 URL 次数调模型。

---

## 5. 用户不等 HTTP：后台任务

速度优化解决的是「算得快」；前后端联调还要解决「页面不超时」。

- SQLite `jobs` 表（WAL）记 `status / stage / message`
- `POST /api/cities/{city}/jobs` 起一条后台线程跑 `run_pipeline`
- 前端 404 时创建任务，每 2 秒轮询进度，完成后拉榜

这不缩短墙钟，但把「首次 5 分钟」从浏览器超时里拿出来。已有榜的城市不重跑。

---

## 6. 成都实测：5–6 分钟，瓶颈不在深筛

深筛拆开之后，成都跑了一遍全流程。时间拆开是：

| 阶段 | 当时怎么跑 | 大约耗时 |
|---|---|---|
| 搜索 5 条查询 | 串行博查 | 十几秒 |
| **抽 20 篇店名** | **一篇一篇 DeepSeek** | **约 3 分钟** |
| 高德匹配 ~64 个店名 | 一个一个打，还 `sleep(0.2)` | 约 1 分钟 |
| 初筛 | 本地 | 可忽略 |
| 深筛 30 家 | 已并发，但仍被逐条抓页拖着 | 约 2 分钟 |

深筛已经不是主因。卡在前面两段还完全串行，以及同店 URL 仍一条等完再抓下一条。

---

## 7. 抽取、高德、同店抓取并行（当前）

按收益从大到小做完三件事：

| # | 改动 | 位置 | 参数 |
|---|---|---|---|
| 1 | 20 篇抽取丢进线程池 | `pipeline/discover.py` | `EXTRACT_WORKERS = 12` |
| 2 | 高德并行，去掉 `sleep(0.2)`；QPS 超限重试 | `pipeline/match.py` | `GAODE_WORKERS = 8` |
| 3 | 同一家店的 URL 一起抓；超时 15s → 连接 3s / 读取 8s | `pipeline/deep.py`、`clients.py` | `FETCH_WORKERS = 8`，全局限 16 路 |

进度回调仍在主线程（`as_completed`），SQLite 写入也在主线程。工作线程只打外部 API、打日志。

本地用假抓取核对过：4 个链接各睡 0.4 秒，墙钟 0.40 秒，确认同店抓取是并行而不是串行。

预估全流程：

| 阶段 | 现在 | 大约耗时 |
|---|---|---|
| 博查 5 条查询 | 仍串行（占 5 QPS 额度） | 10–15 秒 |
| 抽 20 篇 | 最多 12 路 DeepSeek | 十几秒 |
| 高德 ~60 店 | 最多 8 路 | 数秒 |
| 初筛 | 本地 | 可忽略 |
| 深筛 30 家 | 最多 20 个店工人；博查 5 路；抓取 16 路 | 约 1 分钟 |

合计 **大约 1.5–2.5 分钟**，落在 1–2 分钟这一档的上沿。硬底是：每家口碑仍是一次 20–50 秒的模型调用，30 家即使用 20 个工人也得一两波。

当前时间线：

```
发现   [搜×5 串行][======== 抽取 12 路 ========]
匹配                              [高德 8 路]
初筛                                    [本地]
深筛                                      [搜≤5][抓≤16][======== 模型 ≤20 路 ========]
```

---

## 8. 现在的限流与并发

| 资源 | 上限 | 作用 |
|---|---|---|
| 博查搜索 | `BOCHA_LIMIT = 5` | 发现阶段的 5 条查询仍串行；深筛跨店搜索共用这把闸 |
| DeepSeek 抽取 | `EXTRACT_WORKERS = 12` | 只用于发现阶段 |
| 高德 POI | `GAODE_WORKERS = 8` | 超限（`CUQPS` / `10021`）最多再试 2 次 |
| 店工人 | `MAX_SHOP_WORKERS = 20` | 深筛同时处理的店数 |
| 网页抓取 | 每店最多 8、全局最多 16 | 不占博查配额 |

没有换成 `asyncio`：现有 `requests` / OpenAI 同步客户端套线程池即可。等网络时 GIL 会让出，多路 HTTP 可以重叠。

---

## 9. 若还要往 1 分钟压

并发已经叠在外部 API 的等待上，再提速主要靠 **少干一点**，会换店数或证据厚度：

- 短名单 30 → 15：深筛少一半模型调用
- 抽取 20 → 12 篇：发现阶段更短，召回可能变少
- 每店搜索 8 条 → 5 条：少抓几页，材料变薄
- 缩短口碑提示词里的正文截断：单次 `chat()` 从几十秒往下掉

不建议再把发现阶段的 5 条博查查询并行打满——那 5 QPS 马上要留给深筛。也不建议 30 家店同时打满 DeepSeek 而不限工人：费用和限流会先于速度出现。

已经出过榜的城市不要重跑。5–6 分钟（以及现在的 1–2 分钟）只发生在这座城市第一次探。
